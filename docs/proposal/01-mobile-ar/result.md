# Материалы заявки

## Предложение №1: Мобильное приложение и AR

Предлагаем доработать существующее Flutter-приложение, включить его в единый пользовательский контур Экосистемы и встроить AR-модуль с локальным распознаванием, заранее загружаемыми материалами и серверным подтверждением результатов. Предложение включает два алгоритма и последовательность выполнения работ по [п. 2.1.1 порядка оценки](../../evaluation/03.md#quality-1).

[Схема 1 — действия посетителя](flowcharts.md#user-flow) · [Схема 2 — обработка событий системой](flowcharts.md#system-flow)

Описанные ниже решения являются предлагаемой архитектурой. Обследование исходного приложения проводится после заключения контракта. Сведения о текущих API, серверном стеке, качестве кода и составе зависимостей пока отсутствуют; их наличие и пригодность не предполагаются подтверждёнными. Конкретные музейные сюжеты разрабатываются и согласовываются в ходе работ; алгоритмы используют нейтральные обозначения музейного объекта и интерактивного действия.

## 1. Обследование и выбор реализации

В соответствии с [п. 9.8.1](../../technical-specification/09-08.md#редизайн-и-доработка-мобильного-приложения) сохраняем Flutter и начинаем с воспроизводимой сборки переданных исходников. Проверяем архитектуру приложения и сервера, зависимости, права на код, безопасность, производительность, документацию, развёртывание и возможность независимого сопровождения Заказчиком. Отдельно составляем карту экранов и интеграций с профилем, билетами, магазином, лояльностью, уведомлениями и аналитикой.

| Результат обследования сервера | Предлагаемое действие |
| --- | --- |
| Сервер соответствует ТЗ и допускает передачу для самостоятельной эксплуатации | Доработать API и интегрировать существующий сервер с единым контуром; сохранить совместимость на период обновления приложения. |
| Ограничения нельзя устранить доработкой без существенного архитектурного или эксплуатационного риска | Представить Заказчику обоснование контролируемой замены, карту переноса данных и функций, план переключения, сверки и восстановления. Выполнить замену после утверждения решения. |

Оба варианта входят в цену контракта и сохраняют полный состав функций, данных, интеграций и сценариев. Выбор серверного языка и фреймворка фиксируем по результатам обследования, а контракты AR-модуля проектируем независимо от этого выбора.

## 2. Клиент-серверная архитектура

Приложение отвечает за камеру, локальное распознавание, представление материалов и предварительный прогресс. Сервер отвечает за доступ, опубликованные версии сценариев, проверку событий, подтверждённый прогресс и основания начислений. Единый пользовательский контур является источником идентификатора пользователя и актуальных прав; система лояльности — источником подтверждённого баланса.

| Взаимодействие | Передаваемые данные | Результат и ошибки |
| --- | --- | --- |
| Приложение → API каталога | Идентификатор сценария, язык, возможности устройства, известная версия | Манифест: версия, цели распознавания, ресурсы и их хеши, действия, доступная альтернатива. При отсутствии публикации — понятный статус недоступности. |
| Приложение → хранилище материалов | Ссылки на ресурсы из манифеста | Загрузка с проверкой целостности. Незавершённая загрузка не заменяет действующий пакет. |
| Приложение → API сеанса | Авторизованный запрос, сценарий и версия | Сервер создаёт `attempt_id`, связывает его с пользователем и выдаёт условия прохождения. Ошибки доступа не создают чужую попытку. |
| Приложение → API событий | `event_id`, `attempt_id`, версия, номер этапа, тип, данные действия, клиентское время | Сервер возвращает статус события и подтверждённый прогресс. Пользователь определяется по сеансу, а не по произвольному полю запроса. |
| Сервер AR → профиль и лояльность | Подтверждённый результат, основание и ключ операции | Профиль получает прогресс и достижения, лояльность — команду начисления. Недоступность получателя оставляет операцию в очереди. |
| Сервер → аналитика | Идентификатор события, тип, сценарий, этап, результат, обезличенные атрибуты | Доставка без повторного учёта одного события, с учётом основания обработки и согласий. |

API версионируются, документируются и используют защищённый транспорт, проверку схем, ограничения размера и частоты запросов, корреляционные идентификаторы и единый формат ошибок по [пп. 11.4–11.5](../../technical-specification/11.md#требования-к-api-и-интеграционным-контрактам). Логические компоненты могут быть модулями существующего сервера: схема не требует необоснованного выделения каждого из них в отдельный сервис.

## 3. Пользовательский AR-сценарий

[Пользовательская блок-схема](flowcharts.md#user-flow) описывает путь от выбора сценария до подтверждения результата. Приложение проверяет доступность пакета, возможности устройства и разрешение камеры. Для изображения или метки загружается локальный набор целей; QR разрешается только в идентификатор опубликованного объекта, без перехода по произвольной внешней ссылке. Произвольное распознавание любых музейных предметов не предполагается: для каждого объекта заранее задаётся способ привязки.

При отсутствии распознавания посетитель получает подсказки по освещению, расстоянию и положению камеры и может повторить попытку либо открыть альтернативу. Потеря трекинга приостанавливает привязанный контент и предлагает повторно навести камеру, сохраняя уже выполненные шаги. Уход приложения в фон останавливает камеру и воспроизведение; возврат восстанавливает сценарий с проверкой состояния.

| Материал или действие | Реализация и фиксируемый результат |
| --- | --- |
| 3D-объект | Показ относительно распознанной цели, выбор интерактивной точки, разрешённые сценарием поворот и масштабирование; фиксируется действие, предусмотренное условием этапа. |
| Текст и графика | Карточки с последовательной навигацией и доступными подписями; простое открытие карточки не считается завершением задания, если требуется ответ. |
| Аудио | Воспроизведение, пауза, повтор и текстовая расшифровка; событие прослушивания формируется по правилу сценария. |
| Видео | Управление воспроизведением, субтитры и текстовая альтернатива; завершение просмотра проверяется отдельно от открытия видео. |
| Ответ или выбор | Передаются идентификатор задания и ответ; сервер проверяет условие и разрешённое число попыток. Клиент не назначает себе баллы. |

При отказе в разрешении или неподдерживаемом AR устройстве доступны карточки, текст, аудио с расшифровкой, видео с субтитрами и альтернативные действия по [С-11](../../technical-specification/08.md#scenario-c-11) и [п. 13.4](../../technical-specification/13.md#доступность). Условия результата для альтернативы задаются в сценарии; переключение режима не создаёт вторую награду. Интерфейс предусматривает управление средствами доступности, понятный фокус и сообщения об ошибках.

Просмотр общедоступных материалов не требует принудительного входа. Для привязки результата к профилю пользователь проходит авторизацию. Локальное прохождение гостя можно отправить после входа только с явным подтверждением привязки к выбранному аккаунту и серверной проверкой; его принятие и начисление заранее не гарантируются.

## 4. Результаты, защита от повторов и аналитика {#results}

[Системная блок-схема](flowcharts.md#system-flow) отделяет распознавание на устройстве от серверной проверки событий. Кадры камеры обрабатываются локально и в API событий не передаются. Распознавание цели сообщает, какой контент открыть; оно не доказывает само по себе физическое присутствие и не является достаточным основанием для награды.

Сервер проверяет сеанс, принадлежность попытки, основания обработки и необходимые согласия, доступность версии сценария, порядок этапов, допустимость действия и ограничения правила. Отказ от маркетинга не блокирует сервисные операции. Разрешение камеры ОС и согласие на обработку данных учитываются раздельно по [п. 15.4](../../technical-specification/15-04.md). Токены и лишние персональные данные не включаются в журналы.

Для каждого события приложение один раз создаёт `event_id`; при повторной доставке сохраняет этот идентификатор. Сервер хранит уникальную пару «пользователь + event_id», хеш полезной нагрузки и результат обработки. Тот же идентификатор с изменёнными данными вызывает конфликт, а не повтор операции. При параллельной доставке уникальное ограничение и транзакция допускают одно применение события.

Отдельно действует уникальный ключ основания награды: пользователь, сценарий, задание или итог маршрута, правило и разрешённый правилами период/номер повторения. Новая попытка или новый `event_id` не обходят ограничение однократной награды. Повторное прохождение разрешается только в соответствии с настройками; версия сценария сама по себе не открывает повторное начисление.

В одной транзакции сохраняются событие, прогресс и запись исходящей очереди. Получатель лояльности обрабатывает команду идемпотентно по ключу основания. Если начисление выполнено, но ответ потерян, повтор команды возвращает прежнюю операцию. До получения подтверждения приложение показывает «Результат сохранён, начисление ожидается», затем получает подтверждённый баланс из единого контура. Достижения также имеют уникальное основание и историю.

**Пример повтора:** событие `E-42` завершает этап попытки `A-17`. Ответ теряется. Повтор `E-42` возвращает сохранённый результат, не меняя прогресс второй раз. Новое событие `E-43` с тем же основанием однократной награды не создаёт второе начисление. Если доставка команды лояльности повторилась после сбоя, её ключ по-прежнему соответствует единственной операции.

Применяем ограничения частоты, проверки последовательности, срока попытки и аномальных серий действий. Для наград, требующих подтверждения посещения, в ЧТЗ задаётся отдельное проверяемое основание: скопированный QR или клиентское время не принимаются за такое подтверждение. Сомнительные результаты переводятся на проверку. Уполномоченный сотрудник может подтвердить, скорректировать или аннулировать результат с указанием причины; отмена баллов оформляется связанной операцией, исходная история сохраняется. Журнал лояльности содержит уникальный идентификатор, время, основание, источник, баланс до/после и признак повторной обработки по [п. 9.9](../../technical-specification/09-09.md).

Аналитика учитывает запуск, прохождение этапа, завершение, неуспех, отказ, ошибку, использование AR, получение достижения, начисление и отмену баллов по [п. 9.10.11](../../technical-specification/09-10.md#аналитика). Операционные события и события продуктовой аналитики имеют разные цели обработки; состав данных и сроки хранения фиксируются в проектировании. Защита от злоупотреблений раскрывается отдельно по [п. 9.10.10](../../technical-specification/09-10.md#защита-от-злоупотреблений).

## 5. Офлайн-работа и восстановление связи

Для выполнения [п. 9.8](../../technical-specification/09-08.md#мобильное-приложение) предлагаем заранее загружаемый пакет: манифест версии, цели распознавания, 3D, изображения, тексты, аудио, видео, расшифровки, субтитры и альтернативные действия. До загрузки показываем размер и доступное место; перед использованием проверяем комплектность и хеши. Новая версия активируется целиком, старая сохраняется до успешного обновления. Пользователь может удалить материалы; незавершённая очередь результатов при этом не удаляется без предупреждения.

Материалы без предварительной загрузки при отсутствии сети недоступны: приложение объясняет причину и предлагает уже загруженные сценарии. Системные AR-компоненты также должны быть готовы заранее; если их нет, используется загруженная альтернатива. Покупка, изменение баланса и получение новых серверных прав офлайн не имитируются.

Прогресс и исходящие события сохраняются в SQLite до показа локального завершения. Состояния события: «ожидает отправки» → «отправляется» → «подтверждено», «отклонено» либо «требует проверки». Тайм-аут возвращает событие в очередь; повтор выполняется с тем же `event_id`, увеличением интервала и ограничением частоты. Ошибка авторизации приостанавливает отправку до восстановления сеанса; ошибка данных требует исправления, а не бесконечных повторов.

Если попытка создана онлайн, используется её `attempt_id`. Если запуск произошёл полностью офлайн, создаётся локальная попытка; после входа и восстановления связи сервер проверяет её допустимость и устанавливает соответствие локального и серверного идентификаторов. Смена аккаунта не переносит очередь автоматически: отправка возможна только владельцу попытки; выход очищает сеанс и закрывает доступ к его локальным данным.

**Пример прерывания:** посетитель заранее загрузил пакет и начал маршрут, затем потерял сеть. Приложение продолжает локальное распознавание и сохраняет действия. После восстановления связи отправляет очередь в порядке этапов. Если версия отозвана или условия события не подтверждены, сервер возвращает мотивированный отказ либо статус проверки. До серверного решения показывается предварительный прогресс, без обещания баллов. Уже подтверждённые этапы сохраняются по серверной истории; конфликт разрешается по серверным правилам, а не по последней клиентской записи.

| 2. Проектирование | Контракты API, модель попыток и наград, офлайн-пакет, правила доступа, матрица устройств, прототип AR на целевых образцах | ЧТЗ, схемы, спецификации, согласованные зависимости и критерии испытаний. |

Редизайн | Единая дизайн-система: splash, главная, афиша с календарём и фильтрами, событие, музей, филиалы, QR-сканер, вход/регистрация/восстановление, профиль, билеты и QR-билет, история заказов, избранное, лояльность, поиск, уведомления и настройки | Согласованные макеты, компоненты, состояния загрузки/ошибок и доступные варианты экранов по п. 9.8.1. |

Обязательный контент по [п. 9.10.12](../../technical-specification/09-10.md#обязательный-объем-реализации-и-пилотного-наполнения): не менее двух игровых маршрутов, каждый с восемью связанными заданиями; не менее двух AR-маршрутов с согласованными точками и мультимедийными объектами; не менее двух подготовленных и опубликованных аудиогидов. Эти продукты учитываются в общем плане и не заменяются техническим демонстрационным экраном. Количество AR-точек, состав объектов, остановки и продолжительность аудиогидов фиксируются в ЧТЗ к КТ-2; подробные сценарные материалы раскрываются в соответствующих предложениях без повторного учёта производства.

Передаются права на специально созданные результаты, редактируемые исходники контента, реестр лицензий, код адаптеров, API-документация, инструкции воспроизводимой сборки и безопасной передачи ключей. Интерфейс — RU/EN; перевод пилотного музейного контента не требуется. Отсутствие EN-материала отображается явно, с предложением имеющегося русского материала, без пустого экрана.

## 7. План испытаний

По [п. 14.3](../../technical-specification/14.md#совместимость) версии iOS и Android определяются с учётом статистики и требований магазинов. Конкретные номера ОС и модели устройств заранее не назначаем. После обследования составляем согласованную матрицу: платформа, модель, ОС, AR-возможности, системные компоненты, камера, память, размер экрана и режим доступности. Выделяем согласованную нижнюю границу производительности, типовое устройство, устройство с отличающимися характеристиками и устройство без поддержки AR. Распознавание и трекинг проверяем на физических устройствах; эмуляторы применяем для вспомогательных проверок.

| Проверка | Ожидаемый результат |
| --- | --- |
| Распознавание изображения, метки и QR, неверная цель, разные освещение, расстояние и наклон | Открывается только связанный объект; при неуспехе доступны подсказка, повтор и альтернатива. Проверяемые условия и измеримые пороги фиксируются до испытаний. |
| 3D, текст, аудио, видео и интерактивные точки | Правильная привязка и действия, сохранение позиции, субтитры и расшифровки; потеря трекинга не засчитывает действие сама по себе. |
| Нет камеры, отказ разрешения, неподдерживаемое устройство | Понятная причина и доступное альтернативное прохождение, без тупика и без второго основания награды. |
| Нет сети, слабая сеть, неполный пакет, нехватка места, отозванная версия | Загруженные допустимые материалы работают; неполный пакет не активируется; результат имеет явный предварительный статус до проверки. |
| Фон, закрытие процесса, перезапуск, смена аккаунта | Восстановление локального прогресса, сохранность очереди и невозможность отправки результата в чужой профиль. |
| Два параллельных запроса, тайм-аут, повтор события, новое событие с тем же основанием | Одно применение события и одна допустимая награда, сохранённый ответ на повтор. |
| Недоступность профиля, лояльности или аналитики, сбой между фиксацией и доставкой | Очередь восстанавливается; начисление подтверждается один раз; статусы различают сохранённый прогресс и ожидающую операцию. |
| Подмена попытки, версии, ответа, времени или идентификатора цели | Отказ либо проверка по серверным правилам, без доверия клиентскому флагу успеха; запись причины. |
| Согласия, отказ маркетинга, экранный диктор, RU/EN и отсутствие перевода контента | Разделение оснований обработки, доступные элементы, сервисные операции сохраняются, язык материала обозначен. |
| Сквозные интеграции и выпуск | Профиль, билеты, избранное, лояльность и уведомления согласованы между каналами; обновление сохраняет данные; публикация подтверждена в согласованных магазинах. |

Это план будущих испытаний. Протоколы, результаты измерений и подтверждения публикации формируются при выполнении контракта; настоящее предложение не объявляет эти проверки уже пройденными.
